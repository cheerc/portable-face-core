# 診斷 run 操作手冊（W0-a）

這份手冊給**操作者**看。你不需要寫程式、不需要開 Terminal 算任何東西、不需要問任何人。

它回答三個問題：

1. 為什麼這一輪沒有可用的影格？
2. support 視窗為什麼沒有累積到 3 幀？
3. 這一輪花了多久？

## 第 1 步：為什麼沒有可用的影格

每一輪先看 **`frames_sampled`** 和 **`frames_usable`** 兩欄（這兩欄舊 log 就有）。

```
frames_sampled = 0            → A 類：相機整個沒交出影格
frames_sampled > 0
  frames_usable = 0           → B 類：拍了，但每一張都被品質門或「沒人臉」擋掉
  frames_usable > 0           → C 類：有可用影格，問題不在這裡，請看第 2 步
```

| 類 | 你看到什麼 | 這代表什麼 | 你該怎麼做 |
| --- | --- | --- | --- |
| **A** 相機沒交出影格 | `frames_sampled=0` 且 `frames_usable=0` | 相機層完全沒出畫面 | 檢查鏡頭有沒有被東西擋住、macOS 相機權限、是不是被別的程式佔用了 |
| **B** 拍了但全被拒 | `frames_sampled>0` 且 `frames_usable=0` | 畫面有進來，但**每一張都沒通過品質門，或根本沒偵測到人臉** | 對照下面的 `reason_codes` 判斷是哪一種，然後改善光線／距離／畫面 |
| **C** 有可用影格 | `frames_usable>0` | 相機與品質門都沒問題 | **問題在 support 視窗，請看第 2 步** |

### B 類要再看 `reason_codes` 才知道是哪一種

⚠️ **不能只寫「品質門全拒」就結束**，因為實際有三種，處置方式不同：

| `reason_codes` 裡出現 | 意思 | 怎麼改善 |
| --- | --- | --- |
| `all_frames_rejected_quality` | 有人臉，但**畫質**被拒（模糊、太暗／太亮、臉太小、偏頭角度大、遮擋） | 讓光線充足、鏡頭乾淨、臉正對鏡頭、不要遮擋、距離拉近一點 |
| `all_frames_rejected_no_face` | 有畫面，但**沒偵測到人臉** | 讓臉完整出現在畫面裡，避免背光、避免只拍到側臉 |
| `all_frames_rejected_mixed_causes` | 上面兩種**都有發生** | 同時處理兩種 |

### A／B／C 的真實分布（2026-09-30 那批 32 列舊 log）

| 類 | 輪數 | `reason_codes` 簽名 |
| --- | --- | --- |
| A | **11** | `no_frames_captured\|timeout` —— 11 輪全部一樣 |
| B | **5** | `all_frames_rejected_quality\|deadline_exceeded`（2）／`..._mixed_causes\|...`（2）／`..._no_face\|...`（1） |
| C | **16** | `supported_3_frames`（11）／`insufficient_evidence\|support_N_of_3\|best_baseline_matched`（5） |

⚠️ 這批舊 log 裡 B 類的 `frames_sampled` 合計 122、`frames_usable` 合計 0 —— **support 視窗一次都沒開過**。這是判斷 A／B 必須分開的原因：兩者處置方式完全不同。

## 第 2 步：support 視窗為什麼沒有累積到 3 幀

### 先搞清楚「support 視窗」是什麼

系統認一個人，要**連續 3 幀**都指向同一個人且都過門檻（`required_support=3`），才算 `matched`。這個「連續 3 幀」的計數器就是 **support 視窗**。

`reason_codes` 裡的 `support_2_of_3` 表示：**這一輪結束時，視窗裡只有 2 幀。**

### 先認識 `result` 欄（第 2 步的入口）

`result` 是**這一輪的最終判定**，寫在最前面幾欄。它可能出現這些值：

| `result` | 代表什麼 | 第 2 步適用嗎 |
| --- | --- | --- |
| **`timeout`** | **時間到了，還沒認成。** 也就是說：相機有在拍、畫面也進來了，但三幀連續的條件在時限內沒成立 | ✅ **適用** —— 這是本步要診斷的那一類 |
| `matched` | 認出來了，而且三幀都通過 | ❌ 不適用（已成功） |
| `invalid_input` | 這一輪作廢了 —— 多張臉、沒人臉、或相機沒交出影格 | ❌ 不適用 → **回第 1 步** |
| `review` | 有點像但不夠確定 | ⚠️ 看 `reason_codes` 決定 |
| `unknown` | 沒認出來 | ❌ 不適用 |
| `cancelled` / `error` | 你按停止、或程式出錯 | ❌ 不適用 → 回報團隊 |

⚠️ **`result=timeout` 不是畫質問題，是「時間不夠」** —— 那一輪的相機與品質門都已經把影格交出來了（這也是為什麼那種輪次一定 `frames_usable>0`），**是三幀連續性沒在時限內成立**。所以它才是「support 問題」的入口：**畫質有問題的輪次不會走到 `timeout`，它們是 `invalid_input`，歸第 1 步。**

⚠️ **看不懂或沒見過的值**：照 G1 回報團隊，**不要猜**。

### 決定性的分辨步驟

⚠️ **先看 `reason_codes`，不要先看計數欄。** `reason_codes` 裡的 `support_N_of_3` **直接寫著視窗最後停在幾**，那是答案本身；兩個計數欄只是**輔助佐證**，不能單獨拿來判斷（實測有反例，下面寫）。

**第 0 個問題：`result` 欄是不是 `timeout`？**

| `result` 是不是 `timeout` | 第 2 步適不適用 |
| --- | --- |
| **不是 `timeout`** | 這一輪不是「時間到了還沒認成」結束的（可能已經 `matched` 認出來，或因多張臉／沒人臉／相機沒出影格而作廢）。**第 2 步不適用**，回第 1 步 |
| **是 `timeout`** | 往下走。**這就是「support 沒能在時間內累積到 3」的那一類**，不論 `reason_codes` 裡有沒有 `support_N_of_3` |

⚠️ **不要用「`reason_codes` 裡有沒有 `support_N_of_3`」當閘門。** 有些 `timeout` 輪次視窗確實裝過東西，但 `reason_codes` 只有 `deadline_exceeded|best_baseline_unknown`、**沒有 `support_N_of_3`** —— 那正是最需要你診斷的一類，**不能因為少了那個數字就把它判掉**。那個數字只是「最後停在幾」的補充，**不是「是不是 support 問題」的判準**。

> 實測：那個舊閘門會把 **52,488 輪裡的 20,634 輪**判掉 —— 約六成，不是邊界情況。完整數字見本章末段。

#### 情況一：`support_clear_reasons` 有內容

→ **視窗被清空過。** 格裡的內容告訴你是什麼把它清掉的。

| cell 內容 | 意思 | 怎麼改善 |
| --- | --- | --- |
| `score_below_threshold:N` | 相似度掉到門檻（0.363）以下，視窗被清 | 距離拉近、光線改善、讓臉正對鏡頭。**分數是相似度，不是正確率** |
| `margin_below_threshold:N` | 最高分和第二名的差距太小（< 0.1），分不出是誰 | 這通常是環境裡有第二張臉，或有干擾物 |
| `quality_rejected:N` | 畫質被拒，視窗被清 | 改善光線／穩定鏡頭 |
| `no_face_detected:N` | 那一幀沒有人臉，視窗被清 | 讓臉持續在畫面裡 |
| `none_runner_up:N` | 只有一個候選，無法算差距 | 註冊組只有一個人時會發生 |
| `empty_identity_scores:N` | 那一幀沒有任何分數 | 系統側的異常，重跑一次看看是否重現 |
| `input_multiple_faces:N` | **畫面裡有超過一張臉**，視窗被清 | ⚠️ **這一輪作廢，要關掉相機重開，然後重跑一輪單人的** |
| `continuity_jump_detected:N` | 臉的位置突然跳動 | 讓人固定位置、不要移動 |
| `deadline_exceeded:N` | 時間到，視窗當下沒滿就被收掉 | 這一輪本來就沒機會到 3；重跑並讓流程更快完成 |

⚠️ **同一格可能有兩三個項目**（用 `;` 分開，例如 `no_face_detected:1;score_below_threshold:2`）。**那代表這一輪有多種原因輪流發生，全部都要記下來**，不要只挑一個。

⚠️ **這裡的 `N` 和 `support_N_of_3` 的 `N` 意思不同，不要混：**
- `support_N_of_3` 的 N = **視窗最後停在幾幀**
- cell 裡的 `名稱:N` 的 N = **那個原因發生了幾次**
- `quality_rejected:N` 的 N 是次數，而且**看不出是哪一個品質門擋的**（模糊？太暗？臉太小？）。只知道「品質門」，不知道是哪一個。

⚠️ **如果你看到一個本手冊沒列的原因名：不是資料壞掉，是程式新增了新的清空原因。** 把該列的 `support_clear_reasons` 內容抄下來回報團隊 —— 本手冊要補那一項。

#### 有一個原因**永遠不會**出現在這一欄（但它確實存在，所以特別說明）

程式裡還有一個清空原因叫 `auto_match_disabled`，**它不會出現在 `support_clear_reasons` 這一欄**。有兩層理由，兩層都實測過：

1. **在你目前的設定下，那段程式不會執行。** 它只在「設定檔沒有指定臉部位置的連續性上限」時才可能進入，而你目前用的設定檔有指定。
2. **就算設定檔被改掉、讓它真的執行了，它還是記不到這一欄。** 因為它被觸發的時機是「第一張通過門檻的影格」，那時 support 視窗還是空的 —— 沒有東西可以被清掉。實測：強制讓它觸發 6 次，`support_clear_reasons` 仍然是空的。

⚠️ **所以：如果你真的在這一欄看到 `auto_match_disabled`，** 那**不是**上面那條「程式新增了清空原因」的通則 —— **設定檔或程式版本變了。** 請立刻回報團隊，不要當成新的正常情況。

#### 情況二：`support_clear_reasons` 是空的

→ **視窗從頭到尾沒有被清空過。**

⚠️ **這是本手冊最容易誤讀的地方：「空字串」有兩種完全不同的意思，而它們在 CSV 裡長得一樣。**

**而且還有可能連 `support_N_of_3` 都沒有** —— 那時要靠計數欄判斷。**三種情形都在下面：**

| `reason_codes` 裡的 `support_N_of_3` | cell | 這代表什麼 | 怎麼改善 |
| --- | --- | --- | --- |
| **`support_0_of_3`** | 空 | **沒有任何影格進過視窗。** 視窗從頭到尾是空的 | 看 `score_reset_count`：**大於 0** 代表影格有進來但都過不了門檻 → 改善方式同 `score_below_threshold`；**是 0** 代表影格進來了但**被判定為「不算」** —— 這時看 `interval_skip_count`，大於 0 就是**影格合格但來得太密**（間隔不到 200 毫秒），**這不是畫質問題，是節奏問題** |
| **`support_1_of_3` 或 `support_2_of_3`** | 空 | **有影格進過視窗**，只是最後沒累積滿就結束了，而且中途沒被清空過 | 影格是好的但**數量不夠或間隔不對**。讓測試者停留久一點、動作平穩一點，不要快速移動 |
| **⚠️ 沒有 `support_N_of_3`** | 空 | **系統沒告诉你視窗最後停在幾**（`reason_codes` 只有 `deadline_exceeded\|best_baseline_unknown`）。⚠️ **這種輪次視窗可能裝過東西也可能沒有** —— **光看 CSV 無法確定** | 這時**只能靠計數欄推**：見下方「第三種情形怎麼看」 |

**分辨方法一句話：有數字就按數字分，沒數字就按計數欄推。**

⚠️ **「沒有 `support_N_of_3`」不等於「沒有 support 問題」。** 這是本手冊最容易誤判的地方 —— **operator 看到 `result=timeout` 但 `reason_codes` 少了那個數字時，不能就此判斷「這輪沒問題」**。它可能是最需要診斷的一類。

### 第三種情形（沒有 `support_N_of_3`）怎麼看

| `score_reset_count` | `interval_skip_count` | 推論 | 把握 |
| --- | --- | --- | --- |
| **大於 0** | 任意 | 視窗**很可能沒累積到東西**，因為分數門擋下了一些幀 | 中 —— 可能仍有合格幀被清掉 |
| **= 0** | **大於 0** | 影格**都過了門檻**，但**來得太密**所以沒能累積 → **節奏問題**，不是畫質問題 | 中高 —— 這是「影格合格但太密」的典型樣子 |
| **= 0** | **= 0** | ⚠️ **兩個計數欄都是 0，不代表影格達標 —— 它代表「什麼都沒被記錄」。** 可能是影格全被品質門／沒人臉擋下了（那些不記入這兩欄），也可能通過但沒累積。**光看 CSV 分不出來** | **無 —— 不要推論。** 回第 1 步看 `frames_usable` 與 `reason_codes`；仍判斷不出就照 G1 回報 |

⚠️ **為什麼第三種情形的兩個 0 不能推論？** 「視窗本來就是空的時候，影格被品質門或沒人臉擋下，**不會被記進任何欄位**」—— 這種輪次三個欄位（cell、`score_reset_count`、`interval_skip_count`）全部是空或 0，**和「影格都達標」在 CSV 上長得一樣**。實測：那一列的輪次裡，**視窗從來沒有裝過任何東西的比例是 100%**（我的探針）/ 72%（reviewer 的影格集合）。**兩者都指出同一件事：不能推論。**

⚠️ **第三種情形的推論都帶「很可能」，不是確定的。** **這是本手冊做不到的地方**：要確知視窗到底裝過東西，CSV 裡沒有那一欄。**遇到這種輪次又判斷不出，請照附錄 G1 回報，不要硬猜。**

⚠️ **最後的數字可能是 0，但中途被清空過 —— 這兩件事不衝突。** `support_N_of_3` 記的是**最後停在幾**，cell 記的是**中途清空過幾次**。一輪可以「裝到 2 幀 → 被清掉 → 最後停在 0」，那時 `support_0_of_3` 但 cell 有內容。**看 cell 有沒有內容，就知道中途有沒有被清過。**

### 這一節為什麼要這樣寫

上面這套分辨法不是照抄程式碼註解，是**實測出來的**。實跑 `SessionEngine`，窮舉 **52,488 種影格組合**：

**序列空間定義（任何人都可以重算）：**
- **9 種影格結果**：分數過門檻、分數不過、差距太小、品質被拒、沒人臉、沒有身分框、沒有任何分數、只有一個候選（無差距可算）、位置跳動
- **每輪 4 幀**
- **3 個間隔**（每個間隔取 20ms 或 250ms 兩種值）—— 4 幀之間只有 3 個間隔
- **總數 = 9⁴ × 2³ = 52,488 種**

結果：

- **`support_0_of_3`（最後停在 0）且 cell 為空，其中視窗其實裝過東西的：0 輪。**
  意思是：**只要 `support_N_of_3` 是 0 而 cell 是空的，就代表視窗真的從頭到尾沒裝過東西** —— 不會出現「裝過又被清空但沒記錄」的情況。**這是上面分流法能成立的原因。**
- ⚠️ **反過來不成立**：cell 為空但 `support_1_of_3`／`support_2_of_3` 的輪次有 **6,364 輪** —— **視窗確實裝過東西**。所以 **cell 空不等於「從來沒裝過」，一定要搭配 `support_N_of_3` 的數字一起看。**
- **`support_0_of_3` 但 cell **有內容**的有 7,026 輪** —— 這就是「裝到一半被清掉、最後停在 0」。**`support_N_of_3` 記最後數字、cell 記中途清空次數，兩者記的不是同一件事。**

## ⚠️ 三個計數欄不可加總（**這是最重要的一條**）

`support_clear_reasons`、`score_reset_count`、`interval_skip_count` **不可以相加**。

**理由一：它們量的東西根本不同。**

- `interval_skip_count` 數的是「這一幀因為**來得太密**而沒被累積」。**被跳過的影格完全沒有離開視窗**，視窗原封不動。加進「清空原因」裡等於把一件沒發生的事算成發生了。
- `support_clear_reasons` 數的是「**視窗真的變小了**」。
- `score_reset_count` 數的是「分數門擋了幾次」，**不管當下視窗是不是本來就空的**。

**理由二：真正要回答「support 為什麼沒到 3」，只有 `support_clear_reasons` 能回答。** 另外兩欄回答的是別的問題。

**各欄正確的用法：**

| 你的問題 | 該看哪一欄 |
| --- | --- |
| 視窗有沒有被清空過？被什麼清空的？ | `support_clear_reasons` |
| 分數門擋了幾次？ | `score_reset_count` |
| 影格來得太密被跳過幾次？ | `interval_skip_count` |

⚠️ **`score_reset_count` 和 `support_clear_reasons` 是「部分重疊」，兩個方向都不成立。**

意思是：**有些 `score_reset` 會出現在 cell 裡、有些不會；有些 cell 的內容又完全不是 `score_reset` 造成的。** 兩個反例都實測過：

| 反例 | 數值 | 說明 |
| --- | --- | --- |
| **A：不在 cell 裡** | `score_reset_count = 1`，但 cell 只有 `quality_rejected:1` | 分數門擋了 1 次，但那時視窗是空的，**沒有東西被清掉**，所以分數門那一次沒進 cell |
| **B：cell 裡但不是 score_reset** | `score_reset_count = 0`，但 cell 是 `quality_rejected:1` | 視窗被**品質門**清掉，跟分數門無關，`score_reset_count` 自然是 0 |

⚠️ **所以不要把兩者當成包含關係，也不要相加。** 相加會重複計算，也會憑空生出對不上的清空事件。

**真正要回答「support 為什麼沒到 3」，最可靠的組合是：`reason_codes` 的 `support_N_of_3` ＋ `support_clear_reasons`。** 計數欄當佐證就好。

> **已知待修的程式碼註解：** `src/facecore/research/cli.py` 裡 `interval_skip_count` 那段註解寫著「`score_reset_count` is a SUBSET of `support_clear_reasons`」。**那句話把關係寫成了單向包含，但實際是部分重疊、雙向皆非子集**（上面兩個反例分別否定兩個方向）。程式碼的行為是對的，錯的是那句註解的敘述。**以本手冊為準，不要照抄原始碼註解。** 修正會隨 W3 的跟進工作一起進行。

## `probe_kind` / `presenting_identity`：兩欄現在一定是空的

### 這兩欄是幹嘛的

它們是上面那個「有實驗設計的診斷 run」的**記錄欄位**：

| 欄位 | 記什麼 |
| --- | --- |
| `probe_kind` | 這一輪是「target」（測試者有註冊）還是「nontarget」（測試者沒註冊） |
| `presenting_identity` | 這一輪鏡頭前的人是誰（例如 `enroll-07`） |

**有這兩欄，才能把「系統的判斷」和「實際情況」對起來** —— 這是回答「會不會認錯人」的前提。

### 現在為什麼一定是空的（**這是誠實狀態，不是故障**）

空字串的意思是「**沒有記錄**」。它**不是**「不是非目標輪」，也**不是**資料壞掉。

- 這兩欄是「接收欄」—— 程式裡有位置收，但**目前沒有任何輸入路徑可以填它們**。demo App 的介面上沒有地方可以輸入，CLI 的 31 個參數也沒有一個能帶它們。
- 所以每一列都會是空的。**這是誠實反映「這一輪沒有 ground truth」，而 ground truth 只有 operator 知道。**

⚠️ **不要因為看到空值就去修它，也不要自己猜一個值填進去。** 猜一個 `target` 進去，會污染之後所有的跨身分統計 —— 那比沒有更糟。

### W0-b 排程時的記錄規則（**是規則，不是現在就要做的教學**）

| 項目 | 規則 |
| --- | --- |
| 哪一輪填什麼 | 每一輪都要填。**不論結果好壞都要填**，漏填的輪次在統計時要單獨標記，不可當成 `nontarget` |
| `probe_kind` 的合法值 | 只有兩個：`target`、`nontarget`。**沒有第三個值**，也不准空著假裝有值 |
| `presenting_identity` | 測試者在註冊組裡就填其身分（例如 `enroll-07`）；**沒有註冊的測試者，這欄填什麼必須在 W0-b 排程時定義**（例如 `outsider` 之類的標記），不可留空 |
| 誰填 | **operator**，在每一輪結束後立刻填。事後回填會和實際測試對不上 |
| 填不進去怎麼辦 | 目前**就是填不進去**，這是 W0-b 的執行前提，不是 W0-a 的缺口 |

> **已知待修的程式碼註解：** `src/facecore/research/cli.py` 中 `probe_kind` 上方有一段註解寫著「until **W0-a** adds one they are always empty」。**這個前提是錯的** —— W0-a 是純文件工作，不動程式碼。實際上這是 **W0-b** 的工作項。**以本手冊為準。**

| **舊檔改完名還在原地，可以改回來** | 改完就無法知道原本記了什麼 |

**一句話：移走「整個檔案」可以；編輯「檔案裡的資料」不行。** 第 0 步要你做的正是前者。
| **4** | **`support_clear_reasons` 只會告訴你「品質門擋了」，不會告訴你是哪一個品質門**（模糊？太暗？臉太小？偏頭？遮擋？） | 判斷不出是哪一個品質門時，**看 `reason_codes`**：若是 `all_frames_rejected_no_face` 就是沒偵測到人臉（不是畫質問題）；若是 `..._quality` 或 `..._mixed_causes` 就是畫質問題，此時**只能靠改善光線／距離／角度試一次，看有沒有變好**。**要精確分辨是哪一個品質門，必須看錄影或由團隊從程式內部查 —— 這是本手冊做不到的事。** |
| **5** | **程式碼裡有兩處錯誤的註解**（`support_clear_reasons` 與 `score_reset_count` 的關係寫成了單向包含，實際是部分重疊；另一處寫著某個工作項會補上輸入路徑，但那是純文件工作、補不上） | **以本手冊為準，不要照抄原始碼註解。** 這兩處會隨 W3 的跟進工作修正。**你不需要處理它們**，但若你寫程式或讀原始碼，別被那兩句話誤導。 |
| **6** | **有一個清空原因（`auto_match_disabled）在這個 build 上永遠不會出現在 log 裡**，因為目前設定檔有開啟臉部位置連續性檢查 | **你正常情況下不會遇到它。** 万一真的看到，代表**設定檔或程式版本變了** —— **立刻回報團隊**，不要當成新的正常情況。（見第 2 步的說明） |
| **7** | ⚠️ **有些 `timeout` 輪次的 `reason_codes` 裡沒有 `support_N_of_3`** —— 那是「最佳影格落在 unknown band」時發生的。**這種輪次，光看 CSV 無法確定視窗最後停在幾**，只能靠兩個計數欄推論（見第 2 步「第三種情形」） | **不要因為少了那個數字就判斷「這輪沒問題」** —— 它可能正是最需要診斷的一類。**判斷不出來就照 G1 回報團隊，不要硬猜。** 這是本手冊做不到的事：CSV 裡沒有「視窗最後大小」這欄，某些情況下就無從得知。 |
